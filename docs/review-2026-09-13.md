Reviewed root revision `96cdd1f` and llama.cpp submodule revision `7bf600953`. This was a review, not a repair pass. Product code and the plans were left unchanged.

The project has working receipts, arithmetic references, registered weight commitments and real Groth16 proofs for row groups. It does not yet prove a complete operation or next-token inference. Several invalid inputs currently receive acceptance, so the current verifier should not be presented as ready for untrusted public use.

## Findings

### 1. P1: Groth16 accepts activation values outside its claimed arithmetic

The circuit explicitly delegates public `q8`, `s1` and `s2` range checks to the verifier. Neither the website nor the isolated checker implements those checks.

Reproduction: take group 0 of the registered Qwen3 `blk.0.attn_k.weight`, set `q8[0] = 128` and the other activations to zero, and calculate consistent sums. Witness generation and proving succeed. The proof matches the existing registered commitment and passes verification using the checked-in key. The actual website `verify()` function displays ACCEPT. `verify_isolated.sh` also exits 0, with pairing and commitment checks true, while model access and networking are blocked.

This is a proof of the circuit's field equations, but not of the advertised Q8_K integer relation, whose activation range is -127 through 127. The Stage 5 report incorrectly says out-of-range activations fail witness generation.

Fix: specify canonical signed field encoding and enforce all public ranges in a shared verifier, or constrain them in the circuit. Add an adversarial prover test that computes a consistent invalid witness; changing a public value after proving does not test this weakness. Reject values outside the field, malformed decimal encodings and incorrect signal counts as well.

Sources: [circuit, line 16](/Users/luiscosio/Projects/ai-verification/code/llama.cpp/examples/receipts/zk/groth16/qdot_rows.circom:16), [website acceptance, line 143](/Users/luiscosio/Projects/ai-verification/site/template.html:143), [isolated checker, line 24](/Users/luiscosio/Projects/ai-verification/docs/stage5/verify_isolated.sh:24).

### 2. P1: Untrusted public inputs are rendered as HTML

The website inserts the first public signal into `out.innerHTML`. Setting that signal to a short SVG tag with an event handler preserves the complete tag in the result, even though proof verification rejects. This is an HTML injection path capable of introducing active content into the verifier page. Verification rejection does not make the rendering safe.

Confirmed by executing the actual website verification function with snarkjs in Node and inspecting its output. Browser execution was not observed: the browser tool blocked navigation to the local test file, and no workaround was attempted.

Fix: render proof-derived values and errors with `textContent`; validate the public-input schema before verification. Treat uploaded proofs and public JSON as untrusted even on a rejection path.

Source: [result rendering, line 159](/Users/luiscosio/Projects/ai-verification/site/template.html:159).

### 3. P1: Independent registration validation accepts incorrect model descriptions

Reproduction: change the manifest's layer count to 999, replace one tensor entry with a duplicate of another, and recompute the manifest's own ID. `register.py --check` still prints `manifest: valid` against the real GGUF. The tensor count is checked, but uniqueness and completeness of the tensor mapping are not. Architecture hyperparameters are not compared with the file.

Recomputing the ID does not bypass an already pinned honest ID. The problem is earlier: a person using this command to independently approve a new registration can approve a false description. A self-hash establishes internal consistency, not the correctness of the registration.

Fix: validate a versioned schema; require an exact, unique tensor mapping; compare all GGUF-derived metadata; validate supported execution and commitment definitions; bind circuit and verification-key digests into the registration. Distinguish metadata-only validation from commitment recomputation in the verdict.

Source: [registration checker, line 257](/Users/luiscosio/Projects/ai-verification/code/llama.cpp/examples/receipts/zk/register.py:257).

### 4. P1: Replay accepts displayed text that disagrees with the verified tokens

Reproduction: fresh Qwen3 inference produces token 12095, ` Paris`. Change only the receipt's displayed response to `The capital of France is Berlin.` and recompute the content hash. Native replay exits 0 with `accept / bit-exact replay`.

Hashes bind the text string and the token array separately; they do not establish that the two mean the same thing. This was already listed as unfinished work, and remains reproducible.

Fix: use the registered tokenizer to check prompt tokenization and response detokenization, with explicit special-token and text-rendering rules. Until then, display verified token decoding rather than treating the receipt's text as verified.

Source: [replay content checks, line 987](/Users/luiscosio/Projects/ai-verification/code/llama.cpp/examples/receipts/receipts.cpp:987).

### 5. P2: A site build from a clean checkout has no verification keys

`build_site.py` reads keys from the ignored prover `groth16/build` directory, although the public keys are tracked under `registry/circuits`. With that local build directory absent, the builder exits successfully and produces a page with one manifest and zero keys. Reproduced by directing the build-directory constant to an absent temporary directory, without changing the real files.

Current local build keys and all four checked-in keys are byte-identical. This finding concerns reproducibility and future key drift, not evidence of an existing malicious key replacement.

Fix: load published verifier materials from the registry, verify their registered digests and fail the build when a required key is absent. An independently installed verifier should never need prover build artifacts.

Source: [key lookup, lines 17 and 31](/Users/luiscosio/Projects/ai-verification/site/build_site.py:17).

### 6. P2: The demo suppresses generation and replay failures

Both commands end with `| grep ... || true`. This suppresses the executable's failure as well as the harmless case where the log filter matches nothing.

Reproduction: execute the unchanged first three demo steps in a temporary copy, substitute a receipt executable that exits 37, and leave an old valid receipt in the demo directory. Generation fails, the old receipt verifies, replay fails, and the three-step prefix exits 0. The full demo was not rerun for this injected-failure experiment.

Fix: preserve the executable's exit status, use a fresh output directory for each run, and assert that required artifacts belong to the current run. A failed or skipped proof stage must not look like a successful complete run.

Sources: [generation pipeline, line 55](/Users/luiscosio/Projects/ai-verification/run-demo.sh:55), [replay pipeline, line 69](/Users/luiscosio/Projects/ai-verification/run-demo.sh:69).

### 7. P2: The API mishandles valid JSON of the wrong type and blocks other requests

Calling the endpoint with `[]` or `null` produces an uncaught `AttributeError`; invalid JSON and an incorrect object shape correctly produce HTTP 400. The endpoint also calls synchronous `subprocess.run` inside an async handler. In an instrumented test, a one-second verifier call delayed an independent 20 ms timer to 1.005 seconds. A real long-running verification can stall that server worker until the subprocess returns or times out.

Fix: validate a typed request schema and offload verification to a bounded worker or asynchronous subprocess. Keep timeout, upload-size and concurrency policies explicit. These tests called the endpoint directly; they were not an HTTP load test.

Source: [API handler, line 45](/Users/luiscosio/Projects/ai-verification/site/serve.py:45).

### 8. P2: The proposed fixed-point quantizer does not produce ggml's exact quants

The reference chooses the absolute maximum, whereas ggml's reference retains the sign of the first element with maximum magnitude. For a block starting with -1 and otherwise zero, F20 produces quant 127 and a negative scale; the native reference produces quant -127 and a positive scale. Their products can agree after the paired sign change, so this is not evidence that the observed token agreement is false. It is a mismatch in the claimed intermediate semantics and matters when linking proofs or porting kernels.

Also, the reproduction script omits `--frac 20`, so its default run still benchmarks F16 despite F20 being the proposed choice.

Fix: either preserve ggml's signed-maximum convention or explicitly specify and register the alternative. Make the corpus runner select the intended version and precision. Define compatibility criteria before expanding the corpus; selecting F20 after seeing the F16 disagreement is tuning evidence, not a held-out quality evaluation.

Sources: [quantizer, line 159](/Users/luiscosio/Projects/ai-verification/docs/stage4/fixed_point_forward.py:159), [corpus command, line 14](/Users/luiscosio/Projects/ai-verification/docs/stage4/agreement.sh:14).

### 9. P2: `--groth16 --limit 1` does not limit Groth16 checking to one tensor

The limit condition uses `n_commit_checked`, which is incremented only by Orion checking. Instrumenting the expensive commitment function showed 168 Groth16 calls with `--groth16 --limit 1` and no `--commit`, while the printed summary claimed one tensor was checked.

Fix: keep separate counters and report what was actually recomputed. This matters on a memory-constrained machine and when callers intentionally request a bounded check.

Source: [limit accounting, line 282](/Users/luiscosio/Projects/ai-verification/code/llama.cpp/examples/receipts/zk/register.py:282).

### 10. P2: Native replay accepts unsupported receipt versions

Changing a fresh receipt's `receipt_version` to `999.0` still yields `accept / bit-exact replay`. The replay path parses the known fields without first rejecting an unknown protocol version.

Fix: check the supported version and required structure before inference, consistently across Python, Lean and native entry points.

Source: [replay parsing, line 969](/Users/luiscosio/Projects/ai-verification/code/llama.cpp/examples/receipts/receipts.cpp:969).

### 11. P2: Isolation controls do not determine the test verdict

The script exits with the pairing check's status regardless of whether the subsequent model-read and network controls succeed. During the first run, nested macOS sandbox creation was denied, yet the controls printed that the model and network were inaccessible "as intended". A failed control process is not sufficient evidence that the intended sandbox policy was exercised.

A second run with native access successfully created the script's sandbox and reproduced finding 1. Fix the harness to fail if controls demonstrate access, distinguish sandbox startup failure from policy denial, and verify the control resources exist before testing denial.

Source: [isolation controls, line 41](/Users/luiscosio/Projects/ai-verification/docs/stage5/verify_isolated.sh:41).

## Assessment of the plans

The objective and most of the acceptance criteria in `PLAN.md` are appropriately strict. The progress labels and some stage reports do not satisfy them yet:

- **Stage 1:** the backend record claims that listing missing engineering satisfies the exit gate. The current plan explicitly says it does not. A complete private computation still lacks a demonstrated composition and feasibility path under the adopted semantics and budgets.
- **Stage 2:** useful registration exists for the Q4_K integer core, but the mapping validator is incomplete, a second registrar is still missing, and the proven representation does not include all parameters needed for the complete model computation. Circuit/key identities need cryptographic version binding.
- **Stage 3:** incomplete. Row-group integer-core proofs are a narrower checkpoint. Activation quantization, floating/fixed-point scales, full accumulation and operation output are outside the proof.
- **Stage 4:** the F20 reference and 20/20 corpus result are real progress. The mode is not implemented inside llama.cpp, is not yet registered as the complete execution, and has no full-token proof. Measured activation widths are observations, not universal bounds. Boundary commitments and composition are soundness and privacy questions, contrary to the report's suggestion that this is only a capacity choice.
- **Stage 5:** useful component tests, not completion of the plan's full-inference gate. The invalid-activation result directly contradicts the negative-case table. End-to-end memory, storage, cold verification and proof-package budgets have not been demonstrated.
- **Stage 6:** a useful prototype interface, with explicit coverage labels. Its build and untrusted-input handling need repair before publication.

Other inconsistencies to resolve: 10 seconds / 50 MiB in the plan versus 60 seconds / 64 MB in the decision record; 1-16 prompt tokens in the plan versus 64 in stmt/v0; the record does not supply the explicit owner acceptance the plan requires for the fallback arithmetic and revised budgets. Some documents still describe ordinary trace hashes as suitable private boundary commitments, while the plan correctly requires hiding commitments.

Groth16's proof privacy is relative to its full public statement, including activation quants and sums, not merely the weight commitment. The current zero salt makes the registration commitment deterministic. Neither observation alone makes Groth16 cease to be zero knowledge, but the stronger model-privacy and private-activation requirements remain unfinished. The local setup is already disclosed as experimental; changing the ceremony alone does not repair any of the verifier or coverage gaps above.

## Recommended next steps

1. **Make rejection reliable.** Repair public-range checking, HTML rendering, registration validation, version/text checks and the demo/isolation failure paths. Capture the reproduced attacks in one repeatable regression command shared by browser and offline verification.
2. **Make the checkpoint independently reproducible.** Pin circuit, key, setup and verifier digests; load keys from the registry; publish a small known-good package and negative packages; test a clean checkout without weights or prover build output. Then obtain a second registration check.
3. **Correct milestone status and freeze the next statement.** Explicitly choose native arithmetic or the F20 variant, supported prompt limits, hiding boundaries, composition and budgets. Register the versioned constants and quantization convention before porting it.
4. **Prove one complete operation.** Include activation quantization, all weight scales, accumulation, rounding and the output relation. Keep its intermediate values private and measure the complete cost. This is the next technical milestone; another partial-node demo is not a substitute.
5. **Establish whole-token feasibility before a broad kernel port.** Prototype linked operations or a complete small block using the intended ZK construction. Measure peak memory, witness storage, proving and cold verification. Require a credible full-token path before committing to all operators.
6. **Finalize trusted setup and publish after the circuit/interface stabilizes.** Use the intended ceremony, independent verification and full adversarial suite. A public website or OpenRouter integration comes after the serving prover produces a proof of the claimed registered computation.
