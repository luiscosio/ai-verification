# Review repairs, 2026-09-13

The eleven findings in `review-2026-09-13.md` have been addressed for the existing receipt and row-group proof checkpoint. No complete-operation or full-token ZK proof has been added. Changes are local and uncommitted, including changes inside the llama.cpp submodule.

## What changed

| Finding | Repair |
|---|---|
| Invalid Groth16 activations accepted | `zk/groth16/verify.js` now supplies the same policy to browser and offline verification: canonical BN254 encodings, signed q8/s1/s2 ranges, exact shape/signal count, group identity and registered key digest. |
| HTML injection in proof results | Results, errors, labels and registry text are rendered through DOM text nodes. Embedded JSON escapes `<` to prevent closing a script element. |
| Invalid model registration accepted | Registration/v1 validates the schema, unique and complete tensor ordering, all GGUF-derived model metadata, tensor sizes/types/shapes/digests, tokenizer identity, supported execution fields and installed proof-material identities. Commitment recomputation remains explicit and is reported separately. |
| Displayed text disagrees with tokens | Native replay validates prompt tokenization and response token pieces using the model vocabulary, including special-token rendering. Python trace verification invokes the same vocabulary-only helper; it does not run inference. |
| Missing keys on a clean site build | The builder loads keys from tracked `registry/circuits`, verifies their registered digests, checks the verifier source digest and fails on missing materials. Local prover build output is unnecessary. |
| Demo hides failures/stale artifacts | Each invocation uses a new `demo/run.*` directory. Pipeline failures propagate, and a missing Groth16 stage fails the demo. `--fresh` remains a compatibility alias without deleting old runs. |
| API JSON errors and event-loop blocking | Strict public-input checks return HTTP 400; verification uses an asynchronous subprocess. One job is permitted per worker; concurrent jobs return 503. Timeout and cancellation terminate the process and release its slot. |
| Quantizer sign mismatch/default precision | The integer reference preserves the sign of the first maximum-magnitude element. The reference and corpus runner default explicitly to F20. Fixed-point rounding is still a distinct proposed execution mode. |
| Groth16 limit counter | Orion and Groth16 checks have independent counters; `--limit 1` checks one tensor for each requested scheme. |
| Unsupported receipt versions | Native replay rejects unsupported versions and malformed token records before model loading. The vocabulary helper also rejects them. |
| Ineffective isolation controls | The script uses a known readable sentinel, requires permission-denial errors from file and local-socket operations, canonicalizes macOS temporary paths and stops if any control or sandbox startup fails. |

The stricter vocabulary check means `verify_trace.py` now needs a rebuilt `llama-receipts` executable alongside numpy and gguf-py. It loads vocabulary metadata only; it does not evaluate the model. The Lean checker remains an independent hash/arithmetic specification check, not a tokenizer-aware full receipt verifier.

## Registration migration

Qwen3's manifest is now `registration/v1`. It pins canonical JSON verification-key digests, the shared verifier source digest, circuit source digest and the existing setup digest.

- Previous manifest ID: `9a307115056280494830f692a229e226301814152fe1559289658d0a937df222`
- New manifest ID: `a3760bf5b3b43f1bff95afd04d3923813353eb3161ba1176791599497deb9254`

The model file, weight commitments, Groth16 keys and circuit constraints are unchanged. Existing compatible proofs can be verified against the new independently obtained registration. Do not accept a replacement manifest simply because a proof supplies it. Existing registrations without the new material pins are intentionally refused by the hardened verifier.

A metadata-only `register.py --check` is not a full independent commitment audit. Use `--commit --groth16` to recompute commitments; a second registrar and authenticated publication are still outstanding.

The earlier browser local-file policy block was not bypassed. Full model-wide commitment recomputation, the upstream CPU/GPU matrix, a new setup ceremony and end-to-end resource-budget certification were not performed during these repairs.

## Plan status and next work

`PLAN.md`, `TODO.md` and the stage records now distinguish implemented components from passed exit gates. Stage 3 is incomplete: quantization, scales, accumulation, rounding and a complete operation output remain outside the proof. F20 is a candidate execution variant; its corpus agreement is compatibility evidence, not native equivalence. The existing registration's historical 64-token metadata does not silently expand the plan's proposed 1-16-token first full-inference scope.

The plan retains its provisional 50 MiB / 10-second budgets. The older 64 MB / 60-second figures are labeled proposals pending explicit adoption. Ordinary activation hashes are no longer described as hiding boundaries, and composition is identified as a soundness/privacy requirement.

Next milestone: specify and prove one complete operation under an explicit execution variant, including hiding boundary commitments and measured resource costs. Establish a viable full-token composition before a broad kernel port. Independent registration and a production setup remain required before stronger public claims or deployment.
